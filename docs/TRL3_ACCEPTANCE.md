# TRL 3 驗收對照：電郵＋人手銀行轉帳

這是測試對照，不是認證結果。程式測試使用隔離資料及銀行 fixture；真實 Gmail、Google 角色、銀行入帳及自然時間實驗必須由團隊執行並保存證據。付款模式為 `bank_transfer`：客人轉帳後，管理員登入銀行獨立核對，再於工作台確認收款。

登入附加驗證：OAuth state／PKCE／nonce、token 驗簽、到期、名單、CSRF、角色限制、臨床資料投影、登出及獨立執行人紀錄由 `auth*.test.mjs` 驗證；真實 Google 雙帳戶登入待記錄。家屬 `/#enquire` 不需登入、提交不回傳連結或其他個案資料。

自動測試入口：`npm run test:workflow`（引擎＋HTTP＋人手轉帳回歸）、`npm test`（完整瀏覽器人手轉帳套餐及原有流程）、`npm run build`。測試結果以執行輸出為準。

必須補齊的實驗文件：研究問題／預期、測試配置版本及政策值、執行人與角色、起止時間、虛構資料集、實際結果與失敗、截圖／事件匯出、人工覆核及限制。驗證台「驗收清單」可逐項追加，禁止倒填未觀察結果。

目前不需要 Stripe 或 FPS API；以人手銀行轉帳及管理員對數驗證付款關卡，不得描述成自動銀行入帳辨識。銀行核對是真實服務中的人手職責。

### 真實測試步驟

1. 在 Dokploy 確認 `BASE_URL`、`AUTH_MODE=google`、兩個不同角色名單、Gmail SMTP allowlist、`PAYMENT_MODE=bank_transfer` 及三項銀行資料；確認 runtime log 有 `listening on 0.0.0.0:3000`。
2. 管理員用管理員 Google 帳戶登入 `/#staff/email`；資深護士用另一個帳戶登入，分別截圖角色及工作台。禁止共用 cookie；每次換角色先登出。
3. 由 `/#enquire` 建立一個 LIVE 查詢，勾選資料保存及跟進同意。管理員確認 T1 已抵達 Gmail，先 GET 開連結，再按 POST 接受；記錄電郵時間及 Case ID。工作台內的「虛構查詢」只供程式演練，不能當作 LIVE 證據。
4. 按 T8 銀行指示完成一次小額真實轉帳，保留銀行交易時間／參考及收款入帳截圖。家屬提交轉帳資料後，管理員在銀行核對相同參考／金額／時間，再按「確認銀行入帳」。未核對前截圖證明不可派單；核對後才派單。
5. 用護士帳戶的 T3 接單，完成 T16 單位、時間表草稿、資深護士覆核及管理員／Yi 最終確認；保存 T11、工作台 JSON 匯出及事件 CSV。服務開始前用測試安排完成到達／完成，保存 DONE 及 payout 記錄。
6. 另開獨立 Case 做付款逾時：建立報價後不轉帳，記錄精確開始時間；等待自然 24 小時後保存 T10／T10b、狀態及事件。再用另一 Case 做無人接單，派單後自然等待 24 小時，保存 T7／T14b／重發結果。不要用虛擬時鐘代替。
7. 每個項目在上表填 PASS／FAIL／PENDING，記錄執行人、香港時間、commit／設定版本、截圖及失敗原因；管理員與資深護士各自簽名或以受控記錄確認。
